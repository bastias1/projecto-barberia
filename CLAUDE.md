# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**Sunwalk** (name in `lib/plataforma.ts`; formerly Navaja) — SaaS for barber shops: each barbería gets its own page with online booking, shop and a staff dashboard. Started as the site of Barbería BENJVMIN (Valdivia, Chile), now `/benjvmin`.
Production URL: **https://www.sunwalk.app/** (also https://projecto-barberia.vercel.app/)

Stack: Next.js 16 (App Router) + TypeScript + Supabase + Tailwind v4 + shadcn/ui + Zustand + MercadoPago.

## Requirements spec (`Requerimientos.md`)

Functional spec from the thesis report: user stories HU-xx with acceptance criteria (§5), plan matrix (§4), implementation order (§6), modules (§7), business rules (§8), BI KPIs (§9), NFRs (§10), key test cases CP-xx (§11).
- Before implementing or changing a feature, read its HU in `Requerimientos.md`. Reference the HU id in commits/PRs (`feat(HU-02): ...`).
- The spec is the target; the code and DB are what exists. When they disagree, tell the user instead of silently changing either. Business rules from §8 go in the DB (constraints/triggers), plan modules/limits stay as data (never hardcode the §4 matrix).
- Known divergences between spec and current implementation:
  - Roles: spec `propietario`/`administrador` → `usuario_barberia.rol = 'admin'` (plus `profesional`, `cliente`); platform admin → `usuario.rol = 'superadmin'`.
  - Modules: the DB has `agenda`, `ecommerce`, `bi`, `calendario`, `pronostico`. Spec module `soporte_directo` doesn't exist yet — add them as `modulo`/`plan_modulo` rows. Reviews (HU-11) are in every plan by decision, so there is no `resenas` module.
  - Payments: spec (§12.7) changes state only from the webhook; today `/api/checkout/pagar` and `/api/suscripcion/checkout` also record the synchronous Mercado Pago result, with the webhook as the other path.
  - Data model: the spec says it isn't closed; it is now in `DB.sql`/`database.types.ts`. Still propose schema changes and ask before applying them. Migrations are applied through the Supabase MCP, not a `supabase/migrations` folder.
  - Tests: spec expects Vitest/Playwright/k6; only Vitest is configured (DB-level tests in `tests/`).
  - Location data (HU-17: dirección, comuna, región, zona horaria) lives on `sucursal`, not `barberia`.
  - Pilot: the spec names Big Cut; production started with BENJVMIN (`/benjvmin`).
  - Customization: spec §3 puts advanced per-barbería visual customization out of scope; it is being built anyway by decision (Apariencia).

## Architecture

### Supabase MCP Access
You have direct access to the Supabase database via MCP tools (e.g. `execute_sql`, `list_tables`, `apply_migration`).
- **Project:** `plataforma-barberia` (project ID: `jrffkkktryskigbglpit`) — the one in `.env.local`. The old project `iuhmjpqwkueueakybgaz` is no longer accessible (it only still serves the logo images).
- Use MCP tools to inspect schema, run queries, or apply migrations directly — no need to guess table structures.
- Business rules live in the database (triggers): prices, totals, stock, booking validation, plan limits. Read the trigger before "fixing" something in the app.

### Supabase Client Strategy
Three distinct clients — use the right one for the context:
- `utils/supabase/client.ts` — browser client (Client Components)
- `utils/supabase/server.ts` — server client with cookie session (Server Components, Route Handlers that need auth)
- `utils/supabase/service-role.ts` — bypasses RLS. Only for: the MercadoPago webhook, recording the result of a shop payment in `/api/checkout/pagar` (`registrarPagoOrder`) and syncing subscription charges (`sincronizarCobros`) in `/api/suscripcion/checkout` and Dashboard → Suscripción, admin API routes after `requireAdmin()` (`lib/admin-auth.ts`), signed email links after `verifyLink()` (`lib/signed-links.ts`), the barbería's Mercado Pago link (`/api/mercadopago/*`, `tokenBarberia` in `lib/mercadopago-barberia.ts`, Vault RPCs `mp_*`, after checking the session is the barbería's admin; the webhook reads shop orders with the seller's token through `tokenDeVendedor`), the Google Calendar routes (`/api/google-calendar/*`, Vault token RPCs, after checking the session; `sincronizar` runs `sincronizarPendientes` in `lib/google-calendar.ts` over the `reserva_evento_google` queue after the `CRON_SECRET` check), transactional emails (`lib/notifications.ts`), deleting a barbería (`eliminarBarberia` in `app/cuenta/actions.ts` after checking the session is its owner; `lib/eliminar-barberia.ts`), and in `/admin` only changing `usuario.rol`/`deleted_at`, Auth bans and the Auth user/avatar cleanup of `eliminarDatosPersona`, after checking `getSuperadmin()`

Middleware lives at `utils/supabase/middleware.ts` and is re-exported from `proxy.ts` at the root (Next.js requires the file to be named `middleware.ts` or `middleware.js` at root, but the project exports a `proxy` function—this is intentional to avoid conflicts).

### Multi-tenant routing
- `/` — the software's landing page (features, plans read from `plan_suscripcion`). `/registro` — a logged-in user registers a barbería (RPC `registrar_barberia`: the user becomes owner (`barberia.id_propietario`) and admin, first sucursal; a 14-day trial only on the plan flagged `plan_suscripcion.es_plan_prueba` (Pro) and once per account (`usuario.prueba_usada_at`), otherwise the subscription starts `vencida` and the app goes to the payment page).
- `/barberias?q=&region=` — HU-19: public search of active barberías by name or comuna (accent-insensitive, filtered in memory in the Server Component), optional region filter; with no matches it lists the active ones of the chosen region. Linked from the landing.
- `/[slug]/...` — everything of one barbería: home, `agendar`, `tienda`, `cart`, `checkout`, `booking-*` and `dashboard/*`.
- `/[slug]/[sucursal]` — page of one branch (address, map, hours, its barbers). Booking for a branch: `/[slug]/agendar?sucursal=<slug>` (`/[slug]/[sucursal]/agendar` redirects there); with several branches and no `?sucursal`, agendar starts with a "Sucursal" step. Branch slugs can't be the sibling route names (CHECK `sucursal_slug_no_reservado`). `app/[slug]/layout.tsx` resolves it (404 if missing/inactive) and wraps the tree in `BarberiaProvider`. The client pages live in the route group `app/[slug]/(publico)/` (everything but `dashboard`).
- Root-level shared routes: `/login` and `/signup` (take `?barberia=<slug>&next=<path>`), `/auth/callback`, `/resena`, `/cuenta` (account hub: pending invitations, my barberías, `/cuenta/clave` to change password), `/invitacion/[token]` (email link), `/api/*`.
- Legal pages (route group `app/(legal)/`, linked from both footers via `LegalLinks`/`LINKS_LEGALES` in `lib/plataforma.ts`): `/terminos`, `/privacidad` (includes the cookies section: only essential cookies, so no banner), `/reembolsos`, `/eliminar-datos`. They are drafts with `[COMPLETAR]` placeholders pending legal review. `VERSION_POLITICA` (`lib/plataforma.ts`) is the version stored in `consentimiento`; bump it when those texts change.
- Old single-barbershop URLs (`/agendar`, `/tienda`, `/dashboard`…) redirect to `/benjvmin/...` (`next.config.ts`). Those words and the platform routes are reserved slugs (CHECK `barberia_slug_no_reservado`): add new top-level routes there too.

Every query must filter by `id_barberia`. Never hardcode a barbería:
- Server Components: `getBarberiaCached(slug)` (`lib/barberia-server.ts`, cached per request) from `params`.
- Client Components under `/[slug]`: `useBarberia()` / `useBarberiaHref()` (`components/barberia-provider.tsx`) for the id and internal links.
- Services take `idBarberia` as first argument. API routes receive the slug (`?barberia=` or body `barberia`) and resolve it with `getBarberiaBySlug()`; emails/signed links resolve it from the booking/order (`getBarberiaById()`).

### Service Layer
All database logic lives in `lib/services/`:
- `barber-service.ts` — public barber list (RPC `profesionales_publicos`), optionally only those assigned to a branch
- `booking-service.ts` — available time slots (RPCs `dias_bloqueados`, `horarios_ocupados` + `horario_atencion`), optionally for one branch; inactive branches are ignored. Bookings are created by the server action `app/[slug]/(publico)/agendar/actions.ts` via RPC `reservar_como_invitado`, or `reservar_con_cuenta` (`conCuenta`: a logged-in client books as `reserva.id_cliente`, HU-02; staff manual bookings always use the guest path)
- Cancel / reschedule by the client (HU-22): `cambiarReservaCliente()` in `lib/cambio-reserva.ts` → RPC `cambiar_reserva_cliente` (owner with session, a guest booking whose email is the session's confirmed one, or service role after the signed email link; rejects with `FUERA_DE_PLAZO` inside `barberia.plazo_cancelacion_min`, default 120, edited in Mi Barbería; staff are not bound by it). Used by the server action `app/[slug]/(publico)/reprogramar/actions.ts` (`/cuenta` and the page `/[slug]/reprogramar?id=&token=`, which reuses the cancel token) and by `/api/cancel-booking`. It emails the client (`notificarCambioReserva`). Rescheduling keeps barber, service and estado
- `dashboard-service.ts` — barber stats, appointments, clients, client blocking
- `product-service.ts` — CRUD for shop products, image uploads to Supabase Storage (`imgs` bucket)
- `schedule-service.ts` — `horario_atencion` (weekly schedule, per sucursal) and `dia_bloqueado` (blocked dates)
- `service-service.ts` — services (`servicio`), barber↔service linking (`profesional_servicio`)

Services alias columns (`id:id_producto`, `duracion:duracion_min`, …) so the UI keeps simple shapes. Embedded relations come back as object or array: normalize with `one<T>()` from `lib/utils.ts`. PostgREST silently caps results at 1000 rows: a query that can grow past that (all bookings of a barber, etc.) goes through `todasLasFilas()` (`lib/utils.ts`), ordered by a unique column.

Other shared modules: `lib/staff-context.ts` (`getStaffContext(slug)` cached per request; dashboard pages call `requireStaff(slug, { admin })`, which redirects), `lib/roles.ts` (`getRolApp`, per-barbería role), `lib/acceso.ts` (`resolverAcceso`: memberships, superadmin flag and post-login destination in one query; see `GLOSSARY.md`), `lib/barberia-publica.ts` (home page data), `lib/planes.ts`, `lib/datetime.ts` (timezone helpers), `lib/pedido-estados.ts` (order status labels), `lib/review-link.ts`.

`'use server'` files may only export async functions — exporting a type there breaks the module at runtime.

### Role-Based Routing
Roles are per barbería (`usuario_barberia`), so the same user can be admin of one and client of another.
- An admin can also attend clients: "También atiende clientes" in Dashboard → Equipo (`/api/admin/update-user` `atiende`) creates/deactivates their `profesional` row; the role stays `admin` and the slot counts toward `max_profesionales`.
- `admin`, `profesional` → `/<slug>/dashboard` (a platform `superadmin` is NOT staff of any barbería: privacy of its clients; `getRolApp` ignores `usuario.rol`, and the DB helpers `es_admin/es_staff` plus the `*_superadmin` policies leave private tables out — the panel gets counts through RPC `admin_conteos_barberias`) (admin also sees Usuarios, Mi Barbería, Productos, Pedidos)
- `cliente` → `/<slug>`; its account is `/cuenta` (there is no per-barbería profile page: `/<slug>/profile` redirects there)
- After login: `resolverAcceso(supabase, userId, { barberia, next })` in `lib/acceso.ts` (it applies `safeNext` itself; unit tests in `tests/acceso.test.ts`) — `next` always wins (staff included: a barber buying in another barbería reaches its checkout); with only the barbería they came from, staff of that barbería go to its dashboard and everyone else to `/<slug>` (never another barbería's dashboard); with no context a superadmin (`usuario.rol`) goes to `/admin`, staff of exactly one barbería to its dashboard, and the rest (clients, staff of several) to `/cuenta`. Without a session, `/<slug>/dashboard/*` and `/admin/*` are redirected by the middleware to `/login` with the full path as `next` (deep links survive the login). `/login` redirects straight away if there is already a session; the landing shows "Mi panel".
- "Mantener sesión iniciada" (login checkbox) writes cookie `sb-recordar` (1/0). `@supabase/ssr` forces 400-day auth cookies, so the `setAll` of the browser client, server client and middleware pass options through `opcionesCookie()` (`lib/sesion.ts`): with `sb-recordar=0` auth cookies become browser-session cookies.
- Email redirects: signup without a barbería → `/cuenta`; confirmation link opened in another browser (PKCE exchange fails) → `/login?confirmado=1&next=…`; password recovery → the email links to `/cuenta/clave?token_hash=…` (template `recuperar-clave.html` with `{{ .RedirectTo }}`, which must be in Supabase Redirect URLs; `verifyOtp` runs on submit, so it works in another browser) → dashboard or `/cuenta`; invitation → `/invitacion/<token>` → dashboard.
- Everyone creates their own account (signup). Staff join a barbería by **invitation**: the admin invites an email in Dashboard → Equipo (`app/[slug]/dashboard/usuarios`, server actions in `actions.ts`); the person accepts at `/cuenta` or `/invitacion/[token]` (RPC `responder_invitacion`). Invitations can target emails without an account yet. Admins can change roles/especialidad (`/api/admin/update-user`) or remove members, but not other users' email/password.
- `/cuenta` is the only account page: profile (`ProfileForm`), addresses (`AddressManager`), pending invitations and barberías (cards only when there are any), booking history (RPC `mis_reservas`: account bookings plus guest ones made with the account's confirmed email, `private.es_mi_invitado`) and purchases, register a barbería, change password (`/cuenta/clave` asks for the current one when the account has one, RPC `tengo_clave`; Supabase checks it only with "Require current password" on in Authentication settings). Email change: `CambiarCorreo` → template `cambio-correo.html` links to `/cuenta/correo?token_hash=…` (`{{ .RedirectTo }}` must be in Redirect URLs) → `verifyOtp` on button press. Equipo shows "Copiar link" for pending invitations; invite actions return `correoEnviado` so a failed email is visible.
- Signup with `?barberia=` creates a client of that barbería; without it, only the user. Buying in a barbería also adds the client membership.
- Google login: "Continuar con Google" (`components/auth/continuar-con-google.tsx`, on `/login` and `/signup`) uses the Supabase Google provider (email + profile only; the calendar is linked separately, HU-24) and returns to `/auth/callback`, which picks the destination with `resolverAcceso` and sends anyone without a `consentimiento` terminos row to `/cuenta/terminos` (unchecked checkbox → server action inserts terminos + privacidad). Supabase setup: Authentication → Providers → Google with the same Google client, Google redirect URI `https://jrffkkktryskigbglpit.supabase.co/auth/v1/callback`, and the site URLs in Authentication → URL Configuration.
- Consent: signup sends `acepta_terminos`/`version_politica` in the auth metadata; trigger `crear_perfil_usuario` rejects the signup without it (except OAuth accounts, `raw_app_meta_data.provider <> 'email'`, which accept on `/cuenta/terminos`) and records `consentimiento` (terminos + privacidad). Booking records it in `reservar_como_invitado`, registering a barbería in `app/registro/actions.ts`. Checkboxes are never pre-checked.
- Data deletion (Ley 21.719): requests arrive by email (`/eliminar-datos`); a superadmin executes them in `/admin/usuarios` → "Eliminar datos de una persona" (`eliminarDatosPersona` in `app/admin/actions.ts`): RPC `anonimizar_usuario` + `anonimizar_guest` for every guest row with that email, then (service role) the auth user gets an anonymous email, random password and a ban, and its avatar files are removed. Transactions are kept anonymized; the audit log doesn't store the email.

### Platform panel (`/admin`)
For the software's own administrators: `usuario.rol = 'superadmin'` (grant it from `/admin/usuarios`). `app/admin/layout.tsx` calls `requireSuperadmin()` (`lib/superadmin.ts`): not logged in → `/login?next=/admin`, other users → `/cuenta`.
- Pages: Resumen (barberías by state, MRR, payments, trials ending in 7 days), Barberías (filters/search/pagination) and `/admin/barberias/[id]` (extend vigencia, change plan, cortesía, eliminar suscripción (cancels the MP preapproval, row → `cancelada`, payments kept), suspend `barberia.activa`; no entry to its dashboard), Planes (edit/create/archive/delete `plan_suscripcion` — delete only if no `suscripcion` ever used it, otherwise archive; + `plan_modulo` + `plan_limite`; inactive plans are hidden from the landing and Suscripción, existing subscriptions keep `precio_pactado`), Usuarios (search, grant/remove superadmin, suspend), Actividad (audit log).
- Server actions in `app/admin/actions.ts`: each checks `getSuperadmin()`, applies the change with the superadmin's own session (it has `*_superadmin` ALL policies), logs it with `registrarAccion()` into `auditoria_admin` and revalidates. Subscription state helpers and queries: `lib/admin-datos.ts` (`estadoSuscripcion`, `getBarberiasAdmin`, `calcularMRR`).
- Exceptions using service role: `usuario.rol`/`deleted_at` (no column grant) and suspending an account (`auth.admin.updateUserById(id, { ban_duration })`). A superadmin cannot remove their own role or suspend themselves. Cortesía is refused when the barbería has a MercadoPago preapproval.

### Deleting a barbería
Soft delete by its owner from `/cuenta`: cancel the Mercado Pago subscription (abort on failure) → `mp_borrar` → RPC `eliminar_barberia` (service role: `activa = false`, `eliminada_at`, slug `eliminada-<uuid>`, future bookings cancelled and emailed, memberships off; refused with paid undelivered orders). No rows are deleted. Trigger `barberia_proteger` lets only the platform change `activa`, `id_propietario` and `eliminada_at`. DB rule checks live in `tests/sql/` (run each file as one query: it always rolls back and passes if the error starts with `OK`).

### Apariencia (look of a barbería's pages)
- `barberia.apariencia` (jsonb, edited by the admin in Dashboard → Apariencia) holds `secciones` (which home page sections show, in what order) and `tema` (mode, colors, font, card style). Always read it with `leerApariencia` (`lib/apariencia.ts`): the admin can write any JSON through the API and the values end up in CSS.
- Sections and layout: `app/[slug]/(publico)/page.tsx` builds the header and one node per section id; `components/diseno-home.tsx` orders them and places them according to `diseno` (`clasico`, `columna` with a sticky header column on desktop, `portada` with a cover photo behind the header, fading into the page color, from `barberias/<id>/portada/`). The header always goes first; a section without content renders nothing. The branch page has a fixed structure.
- Theme: `cssTema` (`lib/apariencia-css.ts`) overrides the tokens of `app/globals.css` and computes every text color for AA contrast; the default theme emits nothing. `components/apariencia-provider.tsx` (in `app/[slug]/(publico)/layout.tsx`) applies it to every client page, never to the dashboard. A client page's full-height container needs the class `pagina-barberia` so the background pattern shows through. Page and card colors apply only with a fixed mode (light/dark), marked with `data-modo`, which also drives the `dark:` variant and hides the visitor's mode toggle.
- A new card on a client page uses the `tarjeta` class (border and card background, `app/globals.css`) to follow the card style and its colors; shadcn `Card` already does.
- The editor (`components/dashboard/apariencia-editor.tsx`, one `apariencia-*.tsx` file per tab and for the preview) previews the real page in an iframe, sending the unsaved draft with `postMessage` (same origin only); the receiving side is `components/vista-previa.tsx`. Once a draft arrives, the previewed page ignores clicks and keys (scroll and hover still work). ### Payments (MercadoPago)
Shop orders are paid with **Checkout API via Orders API** (card form on the site, 1 cuota). App "Sunwalk" (id `7953152967472826`, MLC).
- **Who gets the money:** subscriptions are charged to Sunwalk's own account (`MERCADOPAGO_ACCESS_TOKEN`). Shop orders are charged with the **barbería's own token** (OAuth, Marketplace model, no Sunwalk fee), so they land in the barbería's Mercado Pago account. The card token is still created with Sunwalk's public key (`NEXT_PUBLIC_MERCADOPAGO_PUBLIC_KEY`); only the backend token changes. Verified in the test environment: an order created with a seller token is readable by the seller's token and not by Sunwalk's (404).
- **Connecting:** Dashboard → Mi Barbería → "Mercado Pago" (admin only). `GET /api/mercadopago/conectar?barberia=<slug>` → Mercado Pago (`auth.mercadopago.com/authorization`, signed `state` with purpose `mp-oauth`, 10 min) → `GET /api/mercadopago/callback` (checks the state and that the session is the same admin, exchanges the code at `/oauth/token`, stores access + refresh token in Vault via `mp_guardar_token`, upserts `barberia_mercadopago`) → back to Mi Barbería with `?mercadopago=ok|error|no-configurado|desconectado|en-uso`. `POST /api/mercadopago/desconectar` deletes the secret and the row (it does not revoke at Mercado Pago). The redirect URL `<site>/api/mercadopago/callback` must be registered in the app (`https` only: localhost is rejected, so test the connect step on a deployed URL or an https tunnel). `mp_user_id` is unique: one Mercado Pago account can't serve two barberías (`en-uso`).
- **Token use:** `tokenBarberia(admin, idBarberia)` (`lib/mercadopago-barberia.ts`) returns the access token, renewing it when it has under 14 days left (the refresh token rotates; it re-reads when another request renewed first). If Mercado Pago refuses the renewal (`invalid_grant`, the owner revoked access) the row becomes `desconectada` and it throws `SinMercadoPago`. Never fall back to Sunwalk's account for a shop payment. `crearOrder(accessToken, body, key)` and `mercadoPagoClient(token?)` (`lib/pagos.ts`) take that token.
- **Without a connection:** the shop stays visible as a catalog; `/api/checkout` and `/api/checkout/pagar` answer 409, `/[slug]/checkout` shows a notice instead of the card form (`useAceptaPagos()`, from RPC `barberia_acepta_pagos`), and Productos / Pedidos show `AvisoSinMercadoPago` to the admin.
- **Order body and integration quality:** `armarOrden` (`lib/orden-mp.ts`) builds the order sent by `/api/checkout/pagar`: `items` (title, quantity, integer `unit_price`, `external_code`, `category_id` — the value `beauty` is a guess, no list in the docs), payer first/last name, `statement_descriptor` (the barbería's name, 22 chars; it goes inside `payment_method`: in `transactions.payments[]` the API answers 400 `unsupported_properties`), and `additional_info` with flattened keys (`payer.authentication_type`, `payer.registration_date`). The browser's Device ID (`window.MP_DEVICE_SESSION_ID`, created by Mercado Pago's `security.js` with `view="checkout"`, loaded by the card form; MercadoPago.js v2 doesn't set it) travels in `DatosTarjeta.deviceId` and is sent as `X-meli-session-id`; `MERCADOPAGO_PLATFORM_ID`, when Mercado Pago assigns one, is sent as `X-Platform-Id`. Order creation uses the SDK's `Order.create` (`crearOrder` in `lib/pagos.ts`; Mercado Pago scores the backend SDK and the Platform ID, which `mercadoPagoClient` puts on every call). The SDK's 402 error drops the created order, so `crearOrder` finds it with `Order.search` by `external_reference`. The shop's card form (`pedirRut`) asks for the cardholder's RUT, validates it (`normalizarRut`, `lib/rut.ts`: modulo 11) in the browser and again in `/api/checkout/pagar`, and forwards it as `payer.identification` (`type: "RUT"`, number like `12345678-5`); it passes through our server but is never stored or logged (the app keeps no RUT: `usuario.rut` stays unused), and an invalid one is dropped without blocking the payment. The subscription form doesn't ask for it. The webhook only logs `mp-connect` events (OAuth link/unlink): their payload isn't in the docs I found.
- **Refunds:** there is no refund code; the admin refunds from their own Mercado Pago panel and the webhook reflects it.
- **Test environment:** OAuth with test accounts needs a test **Marketplace** account that owns its own application (Checkout API, API de Orders, with the redirect URL), a test seller that authorizes it and a test buyer. Authorizing the production app with a test seller fails with `invalid_users_involved`. The test app's number, client secret and public key go in `MERCADOPAGO_CLIENT_ID`, `MERCADOPAGO_CLIENT_SECRET` and `NEXT_PUBLIC_MERCADOPAGO_PUBLIC_KEY`.
- `POST /api/checkout` — creates `pedido` + `detalle_pedido` (DB sets prices and validates stock); body includes `barberia` (slug); returns `{ pedido, monto }` (`monto` = DB total). If stock fails, the order is cancelled
- `/[slug]/checkout` — one page: delivery, address, summary and the card form (MercadoPago.js v2 `cardForm` with `NEXT_PUBLIC_MERCADOPAGO_PUBLIC_KEY`; the `issuer`/`installments`/`identificationType` selects must stay in the DOM, hidden). The pedido is created only on "Pagar" (`/api/checkout`, then `/api/checkout/pagar`); a rejected payment reuses it on retry, a changed delivery/address cancels it and creates a new one, and if the DB total differs from the cart total it stops before charging and shows the new total
- `POST /api/checkout/pagar` — `{ barberia, pedido, token, paymentMethodId, paymentMethodType }`; creates an `Order` (`type: online`, `processing_mode: automatic`, `external_reference` = id_pedido, amount from `pedido.monto_total` as an integer string — CLP has no decimals, `"15990.00"` is rejected with 400 —, `installments: 1`, payer = session email) and records it with `registrarPagoOrder` (`lib/pagos.ts`, which owns every write to `pago`: shop Order, legacy Checkout Pro Payment and subscription charge go through `registrarPago`, idempotent on `proveedor + id_transaccion_externa`, with the low-stock alert after an approved shop payment; tests in `tests/pagos.test.ts`). Every attempt is a new MP order / `pago` row (`id_transaccion_externa` = `ORD…`); a rejected attempt leaves the pedido `pendiente` so the buyer can retry. HTTP 402 = order created but payment failed
- `POST /api/webhooks/mercadopago` — for `order` notifications it reads the order with the seller's token: the notification's `user_id` → `barberia_mercadopago.mp_user_id` → `tokenBarberia`; an unknown seller falls back to Sunwalk's client (a 404 is ignored). Verifies the signature with the SDK `WebhookSignatureValidator` (`data.id` from the query, lowercased) against `MERCADOPAGO_WEBHOOK_SECRET` or `MERCADOPAGO_WEBHOOK_SECRET_ANTERIOR` (old app, for preapprovals created before the switch); handles `order` (upserts `pago`; trigger `aplicar_pago_a_pedido` updates `pedido.estado_pago` and moves paid orders to `confirmado`), `payment` (old Checkout Pro orders) and the subscription topics
- Testing: with test credentials the payer must be a **test buyer user** (Orders API 422; preapproval "Both payer and collector must be real or test users") — set `MERCADOPAGO_TEST_PAYER_EMAIL`, used by `/api/checkout/pagar` and `/api/suscripcion/checkout` (never in production). Test card holder name `APRO` approves, `FUND` = insufficient funds. Chile test cards (official list, Oct 2026; expiry 11/30): credit Mastercard `5416 7526 0258 2580` (CVV 123), credit Visa `4998 4704 7065 8262` (CVV 123), credit Amex `3757 781744 61804` (CVV 1234), debit Mastercard `5597 7917 5464 0466` (CVV 123). The old numbers (Visa `4168 8188 4444 7115`, debit Visa `4023 6535 2391 4373`, debit Mastercard `5241 0198 2664 6950`) are no longer valid. For **subscriptions** use a credit card: debit cards are rejected (`CC_VAL_433`), and the Mastercard has an optional CVV, so its browser token comes without CVV (`Card token was generated without cvv validation`); Amex and the Visa are confirmed to work. These cards are shared by every developer, so a card can come back `max_attempts_exceeded` on its first use: switch cards. After several failed attempts Mercado Pago blocks a test card for a while (`max_attempts_exceeded` in `pago.detalle.payment_status_detail`): alternate cards or wait. In dev, do a full reload after editing `formulario-tarjeta.tsx` (the CardForm mounts once)

### Key Conventions
- **Dates**: Bookings are `timestamptz`. Convert with `lib/datetime.ts` (`toZoned`, `fromZoned`, `todayIn`) using the sucursal timezone (`America/Santiago`) — the server runs in UTC. For dates picked in a calendar use `localDateString()`; never `.toISOString()` for a calendar date.
- **UI language**: All user-facing text is in Spanish (es_CL).
- **Toasts**: `sonner` (`<Toaster />` in root layout). Import `toast` from `"sonner"`.
- **Accessibility**: each page marks its main content `<main id="contenido">` (target of the "Saltar al contenido" link in `app/layout.tsx`). Use `<Button asChild><Link/></Button>`, never a `<Button>` inside a `<Link>`. Every input needs a `<Label htmlFor>`.
- **Dark mode**: `next-themes` with `ThemeProvider`. Use the semantic tokens (`bg-background`, `text-muted-foreground`, `border-border`, `bg-brand`…) from `app/globals.css`, never paired `zinc-*`/`dark:` colors. Palette: white/neutral with a mint accent (`--brand`, used as a fill with dark text); dark mode is its own palette. Tenant pages (`/[slug]` home, `agendar`, `tienda`, `cart`, `checkout`) use the same tokens. Booking steps share `components/booking/{opcion-card,acciones-paso}.tsx` (sticky bottom action bar, select then Continuar); the store shell is `components/shop/tienda-shell.tsx`. Platform pages (`/`, `/barberias`, `/login`, `/signup`, `/registro`, `/cuenta`, legal) share `components/plataforma/` (header with mobile menu, footer, brand mark, product views). Titles use the `display` utility (Host Grotesk, medium, sentence case).
- **Soft deletes**: Products and services use `activo: false` for archiving rather than hard deletes, to preserve sales/booking history. `getActive*` functions filter on `activo != false`.
